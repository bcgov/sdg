# AGENTS.md

Repository facts for automated coding assistants. Teams may edit or remove this file.

## Layout

- pnpm + Turborepo monorepo: `apps/` (React + Vite, NestJS), `packages/` (Node/React libraries, Vite library mode), `tooling/` (repo-only `@repo/*` config packages: `typescript-config`, `vite-config`, `vitest-config`, `playwright-config`).
- Each app owns its `.env.example` (no root one); `.env` / `.env.*` are gitignored everywhere.
- Tool versions live in the pnpm `catalog:` in `pnpm-workspace.yaml`; reference them as `"catalog:"` and workspace packages as `"workspace:*"`. pnpm settings belong in `pnpm-workspace.yaml`, not `.npmrc`.
- Workflows: `.github/workflows/` (PR deploys via `reusable-deploy.yml`, tests via `reusable-tests.yml`).
- `compose.yaml` runs the local stack (dev commands behind Caddy at `https://sdg.localhost`) with every `node_modules` as a named volume: a new workspace package needs its `node_modules` volume added to `x-workspace` and `volumes:` there.

## Build, test, run

- `pnpm build | dev | typecheck | test | test:e2e` run through Turborepo; `pnpm lint` (oxlint, type-aware), `pnpm format` / `format:check` (oxfmt) and `pnpm test:all` (Vitest projects) run at the root.
- TypeScript 7 has no compiler API: don't add tools that need it (e.g. vite-plugin-dts). Libraries emit `.d.ts` with `vite build && tsc -p tsconfig.build.json`. React libraries use extensionless relative imports; Node libraries (consumed by NestJS apps on `nodenext`) use `.js` relative imports so their emitted `.d.ts` resolve.
- NestJS apps build with the Nest CLI on TypeScript 6 (`"typescript": "catalog:ts6"`), which still has the compiler API; constructor injection uses explicit `@Inject(...)`.
- portal-api validates requests with zod through the global `StandardSchemaValidationPipe`: declare schemas inline (`@Body/@Query/@Param({ schema })`) and pass response schemas to `@ApiOkResponse({ standardSchema })` for OpenAPI. No DTO classes or class-validator.
- portal-api logs a caught error as `logger.<level>({ msg, error: describeError(error) })` (`describeError` from `@repo/server-core`, `packages/server-core/src/describe-error.ts`: allow-listed fields plus the `cause` chain). Never `logger.warn(msg, stack)`: nestjs-pino drops the stack. Never under `err`: pino's error serializer rebuilds the summary and drops its cause.
- Load tests: k6 scripts in `tests/load` (not a workspace package; k6 runs the `.ts` with explicit `.ts` imports; typecheck via `tsc -p tests/load` in root `typecheck`; `@types/k6` from the catalog). Run with `BASE_URL=… pnpm test:load`; never against PROD.
- Tooling packages ship `.ts` source run by Node type stripping: use explicit `.ts` relative imports and erasable syntax only.
- Workspace tsconfig layout: `tsconfig.json` is a solution file referencing `tsconfig.app.json` or `tsconfig.lib.json` (src), optionally `tsconfig.test.json` (tests needing `node`/`vite/client` types), and `tsconfig.node.json` (`*.config.ts`); `typecheck` runs `tsc -b`. Emitting packages add `tsconfig.build.json` extending a `@repo/typescript-config/*-build.json` preset.
- `defineReactAppConfig` appends override plugins after `react()`. A plugin that must run before it (e.g. TanStack Router's `tanstackRouter()`) goes in front: `mergeConfig({ plugins: [plugin()] }, defineReactAppConfig(...))`.
- The production edge CSP (`apps/portal-web/caddy`) has no `'unsafe-inline'` styles. The bcgov design system's CSS loads as adopted stylesheets: `defineReactAppConfig` includes `adoptedStyleSheets()`, which rewrites the package's `styleInject` at build time. Any other fixed `<style>` a library injects needs its `'sha256-…'` in `caddy/Caddyfile` (`security_headers` argument 2), which `apps/portal-web/src/csp-hashes.test.ts` checks. Don't add `style` attributes in markup or `setAttribute('style', …)`; React's `style` prop and Lit's `styleMap` are fine.
- The portal's header is the `<sdg-header>` Lit web component in `packages/sdg-header` (`@repo/design-system`'s `header` subpath re-exports the bcgov React `Header` and is not for app use; console-web has its own sidebar shell instead of a header). React apps that show it use the typed `<SdgHeader>` from `@repo/sdg-header/react` (React 19 only; portal-web wires it in `components/site-header`). Function inputs are named `*Fn` (`signOutFn`, `navigateFn`) because React 19 treats `on*` props on custom elements as event listeners.
- `packages/sdg-header` is a browser library: `@repo/typescript-config/browser-library*.json` presets, `defineLibraryConfig({ platform: 'browser' })`, `.js` relative imports. It builds `dist/index.js` and `dist/react/index.js` (registry; lit and react external, react an optional peer) and `dist/cdn/sdg-header.js` (`vite build --mode cdn`, self-contained). Entries register the element by calling `defineSdgHeader()`, never with a bare side-effect import, which the build can drop. Nested Lit templates inside `<svg>` must use the `svg` tag, not `html`.
- `<sdg-header>` CSS uses `var(--bcgov-token, <token value>)`; `tokens.test.ts` fails when `@bcgov/design-tokens` changes a value. `logo.test.ts` fails when the upstream logo changes: run `pnpm --filter @repo/sdg-header generate:logo`.
- Production images (`apps/{portal-web,portal-api,console-web,console-api,gateway-api,core-api}/Dockerfile`, `packages/database/Dockerfile`) build from the repo root (`podman build -f <dir>/Dockerfile .`); the edge builds from `apps/portal-web/caddy`. Server apps use `pnpm deploy --prod` (not `--legacy`, which re-resolves). Every image must start with all capabilities dropped: Caddy binaries must carry no file capability (`XCADDY_SETCAP=0`, `setcap -r`). Check with `scripts/images-smoke.sh`.
- Three apps, one database: portal-api (residents, BCSC, cookie `portal.sid`) and console-api (privileged government users, IDIR, cookie `console.sid`) are thin BFFs on `@repo/bff-core` that forward `/api` to core-api with the user's access token; core-api owns the `core` schema and the rules. Each service has its own Postgres login and schema (`core`, `portal`, `console`; init SQL in `packages/database/dev-postgres/init-roles.sql` mirrors `charts/postgres`); the BFFs migrate only their sessions. core-api tells the clients apart by `PORTAL_CLIENT_ID` and `CONSOLE_CLIENT_ID`.
- BFF settings and tests are shared: env from `bffEnvShape()` (`@repo/bff-core`), module options from `bffOptionsFromEnv()` (`@repo/bff-core/nestjs`), and each BFF's `src/testing/app.ts` is a `bffTestKit()` config (`@repo/bff-core/testing/nestjs`: real AppModule, fake IdP, core-api stub, PGlite). Upstream stubs build on `startHttpStub` (`@repo/server-core/testing`), which gateway-api uses too.
- console-api's sign-in upserts the principal in core-api; a refused one (no `admin` client role) is sent through Keycloak end-session to `/not-authorized`. console-web (`apps/console-web`, React, same Caddy image pattern as portal-web) shows the service-account registry, backed by core-api's `/api/v1/console/service-clients` (console client only) and `/api/v1/gateway/me` (the gateway check). console-web's sign-in and not-authorized pages are a centered card; every signed-in page sits in its own sidebar shell (`src/components/app-shell`: icon-rail collapse, ⌘K command palette, account menu, mobile panel) behind the `_app` route guard, built from `@repo/design-system`. Its only direct `react-aria-components` use is the palette, and the catalog pins that to the version bcgov depends on (`src/csp-hashes.test.ts` checks its fixed `<style>` hashes).
- Any app that renders FontAwesome icons (`@repo/design-system/icons`) sets `config.autoAddCss = false` and imports `@fortawesome/fontawesome-svg-core/styles.css` (console-web's `src/font-awesome.ts`, called from `main.tsx` and `test-setup.ts`): otherwise the first icon injects a `<style>` the edge CSP blocks.
- The edge (`apps/portal-web/caddy`) routes by Host: the portal host is the catch-all (`/api*` to portal-api, rest to portal-web); `CONSOLE_HOST` (`<release>-console`, locally `console.sdg.localhost`) goes to console-api (`/api*`) and console-web; `GATEWAY_HOST` (`<release>-gateway`, `gateway.sdg.localhost`) sends `/api*` to gateway-api and answers the rest itself with a Nest-style JSON 404 (`common.caddy` `api_only_not_found`; gateway-api's `/healthz` and `/metrics` stay off the edge). A host matcher whose upstream URL is unset answers 503. Chart hosts: `global.host`, `global.consoleHost`, `global.gatewayHost`.
- `KEYCLOAK_CONSOLE_CLIENT_ID` is a deploy input (`scripts/deploy-values.sh`, per GitHub scope, checked by `scripts/setup-environments.sh`): it sets `console-api.keycloak.clientId` and `core-api.keycloak.consoleClientId`. console-api's Vault secret defaults to `<role>/console-api` (`SESSION_SECRET`, `KEYCLOAK_CLIENT_SECRET`); `CONSOLE_VAULT_SECRET_PATH` overrides it as `VAULT_SECRET_PATH` does portal-api's (TEST shares the nonprod role with PRs, so it needs its own paths). Locally `apps/console-api/.env` is optional; without it only the console host answers 502.
- gateway-api (`apps/gateway-api`) is the service accounts' entry point on `@repo/server-core` only (never bff-core; no database, session, login or secret; env `CORE_API_URL`). It checks shape only (KTD12): 401 itself to a missing or non-Bearer `Authorization`, 405 to every method but GET (HEAD included), 404 outside `/api/v<N>/gateway/*`, all without calling core-api; otherwise it forwards with the caller's `Authorization` unchanged (the `Forwarder`'s token supplier passes it through) and relays core-api's answer, 401/403 included. Its readiness checks nothing beyond liveness, so a core-api outage is a 503 per request.
- Helm charts live in `charts/` (one per app/service, `common` library, `sdg` umbrella; see `charts/README.md`). After a chart change run `pnpm test:charts` (needs the helm-unittest plugin and kubeconform). Map values that carry platform defaults (e.g. `ingress.annotations`) stay `{}` in values.yaml and fall back in the template, since Helm merges maps instead of replacing them.
- Postgres keeps about `max(max_wal_size, wal_keep_size)` of WAL (Patroni's default reserve is 128MB), so keep both at a quarter of the data volume or less (`postgres.parameters` in `charts/sdg/values-<env>.yaml`).
- Deploys to OpenShift run from GitHub Actions (PR open, merge), not from a workstation
- Observability (Grafana LGTM + Prometheus, Alloy as the only collector; ADR 0001) is opt-in at every layer: missing config means nothing is wired up, never an error. portal-api always starts the OpenTelemetry SDK (`src/instrumentation.ts`, preloaded with `node --import`) because it produces `/metrics` (`@opentelemetry/exporter-prometheus` on the app port, no prom-client), but exports traces and logs only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; tests that need instrumented Express start it with `bootstrapTelemetry({ serviceName, env: {} })` from `@repo/server-core/telemetry` (it registers the import-in-the-middle hooks) before importing the app; the edge serves `/collect` and `/telemetry.json` from `import collect_{$TELEMETRY:off}`; portal-web loads Faro only when `/telemetry.json` says enabled; the charts render telemetry env, `sdg.gov.bc.ca/scrape*` annotations, and scraper NetworkPolicy rules only when `global.observability` is set (`common.scrapeAnnotations`, `common.scraperIngressRule`), which `scripts/deploy-values.sh` does only when `OBSERVABILITY=true`. New telemetry follows the same rule. Charts never create RBAC (the deploy account can't): Alloy's pod-discovery Role comes from `scripts/setup-openshift.sh --observability`.
- `charts/observability` is its own release (`observability.yml`), not part of the `sdg` umbrella: `<plate>-tools` collects from dev and test, `<plate>-prod` from prod only. Its configs live once in `charts/observability/files/`, loaded by the chart and bind-mounted by `compose.observability.yaml`; change them there, never in a copy. Pods that should be scraped need `app.kubernetes.io/part-of: sdg` plus the scrape annotations; skip `isQuietPath` paths in any new per-request telemetry.
- Namespace storage quotas are small (`<plate>-tools`: 1Gi of PVC in total). Size volumes per environment, and put data that can be lost on restart on a `sizeLimit` emptyDir (ephemeral storage isn't under the PVC quota), as `charts/observability` does with `persistence.<component>.enabled: false`.

## Shared actions

- Uses bcgov shared actions and workflows (`bcgov/action-*`, `bcgov/actions/*`, `bcgov/actions-openshift/*`, `bcgov/quickstart-openshift-helpers`). Use them as provided; don't copy or fork them.
- Never pin `@main`. Pin bcgov shared actions to a published release SHA with a `# vX.Y.Z` comment.
- Vanity Route TLS (`bcgov/actions-openshift/route-tls`) is strictly managed via the standalone on-demand workflow (`.github/workflows/route-tls.yml` with `workflow_dispatch`). Never embed `route-tls` into `merge.yml`, `release.yml`, or continuous deployment pipelines.

## Settings

- Automated agents must not change repository or organization settings. Settings changes are made by a person on the team with the setup scripts in `scripts/`; agents may run them only without `--apply`, which previews.
- After a repository is created from the template, suggest running `scripts/setup.sh`.
